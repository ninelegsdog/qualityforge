# Быстрый старт

Практический путь от свежего клона до агента, который читает настоящее падение.
Все команды здесь рассчитаны на то, чтобы их выполнить и посмотреть, а не
прочитать. Если какая-то ведёт себя не так, как написано ниже, это баг — стоит
сообщить о нём.

[README](../README.md) описывает, что это за проект и зачем. Этот документ
описывает, как им пользоваться ближайшие десять минут.

## Требования

| Нужно              | Версия                                                  |
| ------------------ | ------------------------------------------------------- |
| Node.js            | 22 или новее. Node 20 закончился в марте 2026           |
| Драйвер Playwright | ставится через `npx playwright install`, не глобально   |
| Python 3           | только для `npm run mcp:check*` и `npm run ci:validate` |

`npm run verify` намеренно не требует Python, чтобы основная часть проекта
оставалась доступна на машине только с Node.

## 1. Установка

```bash
git clone https://github.com/ninelegsdog/qualityforge.git
cd qualityforge
npm ci
npx playwright install --with-deps chromium
```

В CI `npm ci` идёт с отключёнными lifecycle-скриптами; локально это не важно,
потому что проекту не нужен код, исполняемый при установке. `--with-deps`
ставит системные библиотеки браузера и на Linux требует `sudo`.

## 2. Прогон сюита

```bash
npm test
```

Команда поднимает встроенное демо-приложение из `fixtures/` на
`http://127.0.0.1:4311`, прогоняет 139 спеков и гасит сервер. Свежий клон
проходит зелёным без конфигурации и без обращения к чужой сети.

Два пропущенных теста — намеренно, см. шаг 3.

Открыть отчёт:

```bash
npm run report
```

Отчёт раздаётся на `http://localhost:9323` и остаётся на переднем плане до
Ctrl+C. Это поведение Playwright, а не зависание.

## 3. Увидеть настоящее падение с доказательствами

Ядро обещания проекта — падение оставляет достаточно данных, чтобы его
разобрать. Это проверяемое утверждение, поэтому для него есть тест: он падает
намеренно и пропускается, пока его не попросят:

```bash
QUALITYFORGE_EVIDENCE_CHECK=1 npx playwright test tests/smoke/evidence-pipeline.spec.ts
```

Код выхода ненулевой — так и задумано. После этого:

```bash
ls test-results/
```

В каждом каталоге падения лежат скриншот, видео и `error-context.md`. Трейс
смотреть так:

```bash
npm run report
```

При разборе настоящего падения трейс-вьюер полезнее скриншота и видео: он
даёт снимок DOM на каждом действии плюс полный журнал сети, чего не дают ни
скриншот, ни видео.

Сам `error-context.md` стоит прочитать целиком. Playwright уже пишет его как
инструкцию для ассистента — «explain why, be concise, respect best practices»,
а затем имя теста, его расположение, ошибку и диф ожидаемого. Это бесплатно,
и QualityForge ссылается на этот файл, а не переписывает его.

## 4. Превратить падения в артефакты

Упавший тест полезен только если падение можно прочитать позже, ничего не
перезапуская:

```bash
npm run defects:collect
```

Команда читает JSON-отчёт последнего прогона и пишет по одному нормализованному
артефакту на каждое падение в `artifacts/defects/<runId>/`. Прочитать один:

```bash
cat artifacts/defects/*/*.v1.json | head -40
```

Код выхода — это гейт: `0`, когда пороги соблюдены, `1`, когда нарушены, `2`,
когда сбор невозможен. В примере выше выход `1`, потому что упали все спеки, а
`thresholds.maxFailureRate` равен `0.05`. Это работающий гейт.

Контракт описан в [`defect-schema.md`](defect-schema.md). Он версионируется, а
ломающее изменение — мажорный бамп, поэтому артефакт, записанный сегодня,
останется читаемым.

## 5. Дать агенту прочитать доказательства

Сервер работает только на чтение и говорит по MCP через stdio. Сначала запустить
его руками:

```bash
npm run mcp
```

Он печатает баннер в **stderr** и ждёт кадров JSON-RPC на stdin, оставаясь на
переднем плане, пока его не закроют. В stdout не должно уходить ничего, кроме
кадров протокола — посторонняя строка лога делает поток повреждённым. Проверять
его правильно так:

```bash
npm run mcp:check:all
```

Команда запускает настоящий бинарник через настоящую трубу, проверяет, что в
stdout идут только кадры и больше ничего, и пробует три способа выйти за пределы
каталога артефактов — обход через `..`, обход через percent-encoding и
абсолютный путь — и требует, чтобы все три были отвергнуты. Свои данные для
проверки она производит сама, прогоняя шаг 3, поэтому работает и на чистом
клоне, и на зелёном коммите.

Чтобы подключить клиента, добавьте это в его конфигурацию MCP. Это форма
OpenCode v2.0.16 — проверено копированием блока в `opencode.json` и реальным
подключением. Kilo и MiMo не проверялись и могут ждать другую форму:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "qualityforge": {
      "enabled": true,
      "type": "local",
      "command": [
        "node",
        "/absolute/path/to/qualityforge/node_modules/tsx/dist/cli.mjs",
        "/absolute/path/to/qualityforge/src/mcp/index.ts",
      ],
    },
  },
}
```

После этого `opencode mcp list` должен напечатать `✓ qualityforge  connected`.
Запускайте его повторно, прежде чем верить выводу: в каталоге, который OpenCode
ещё не видел, первый запуск или два печатали `No MCP servers configured`, а
настоящий статус приходил через несколько запусков — при вполне корректном файле
конфигурации.

Три замечания, подробности в [README](../README.md#the-mcp-server):

- **Оба пути абсолютные — намеренно.** Клиент запускает сервер из _вашего_
  рабочего каталога, а не из этого чекаута, поэтому относительный корень
  указывает туда, где ничего нет. Тогда сервер откатывается к этому чекауту —
  но помогает это только если шаг 4 уже создал `artifacts/defects/`. Если нет,
  сервер завершается, и клиент сообщает только `failed: Connection closed`.
- **`["npx", "tsx", ...]` тоже работает** и короче, но отвечает в несколько раз
  медленнее формы с `node` выше. Если клиент отказывается подключаться, начните
  именно с этой замены.
- **`opencode mcp add` пишет `mcp.servers.<name>`**, а не `mcp.<name>` выше.
  OpenCode v2.0.16 принимает обе формы; просто в ревью они будут отличаться.

Флаг `--root <dir>` отдаёт артефакты из другого места, а не из `artifacts/defects`
по умолчанию.

| Инструмент               | Что отвечает                                                           |
| ------------------------ | ---------------------------------------------------------------------- |
| `quality_get_latest_run` | Счётчики прохода и падения, длительность, прошёл ли гейт               |
| `quality_list_failures`  | Компактные записи: id, статус, место теста, флаки                      |
| `quality_get_defect`     | Один дефект целиком, вместе с сигналами консоли, сети и ошибок страниц |

Есть и промпт `triage_failure`, который требует фактов раньше гипотез.

## 6. Направить на своё приложение

```bash
cp .env.example .env
```

Задайте `BASE_URL` в `.env`, затем:

```bash
npm test
```

Всё остальное — селекторы, фикстуры, пороги — специфично для проекта и
принадлежит каталогу `tests/`. В `config/project.json` лежат адрес приложения
под тестом, политика доказательств, пороги гейта и место записи артефактов; файл
проверяется при загрузке и сообщает обо всех проблемах сразу, с точным путём.

Свои тесты должны импортировать из встроенной фикстуры, а не из
`@playwright/test`:

```ts
import { expect, test } from "../fixtures.js";
```

Именно это изменение импорта автоматически включает сбор сигналов консоли,
ошибок страницы и сети. Правила для тестов — в [`AGENTS.md`](../AGENTS.md),
приоритет локаторов — в [`selectors-and-testid.md`](selectors-and-testid.md).

## 7. Когда что-то не работает

**`npm test` не может поднять демо-приложение.** Занят порт 4311. `BASE_URL` его
переопределяет, но тогда встроенной сюите нечего тестировать. Освободите порт.

**Нет скриншота или видео.** И то и другое — `only-on-failure` и
`retain-on-failure`. Проходящий тест не производит ни того, ни другого, и это
так задумано. Сырые файлы ищите в `test-results/`, а не в `playwright-report/`.

**Нет трейса.** Политика — `on-first-retry`. Локальный прогон не делает повторов,
поэтому передайте `--trace on`, когда он действительно нужен.

**`quality_list_failures` возвращает пусто.** Правильное поведение на зелёном
прогоне: падений нет. Шаг 3 создаёт их намеренно.

**Локально зелено, в CI красное.** Выполните `npm run verify`,
`npm run ci:validate` и `npm run mcp:check:all` в этом порядке — CI делает ровно
те же три вещи, в том же порядке.
